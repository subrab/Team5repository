# Instruction: D4 Focused POC / validation

**Version:** 2.2 · **Owner:** Muthuvel · **Stage:** Validation · **Output schema:** Markdown, fixed headings · **Builds on:** D2, D3 · **Jury marks:** 20 · **Length:** about 1 page

## 1. Purpose
Produce the POC / validation evidence: what one important architecture question was tested, and what was learned.

## 2. Role
You are acting as a solution engineer reporting the evidence from one focused experiment.

## 3. Objective
Create D4: Focused POC / validation. Done looks like: The evidence answers one meaningful architecture question. A full application is not expected.

## 4. Input Required
- CASE: the challenge
- TEAM DOCUMENTS: the latest D2 and D3
- OWNER'S NOTES: the POC question, what was built or run, and the ACTUAL RESULTS
- POC TRACEABILITY MATRIX: generated from the repository (Requirement -> Spec -> Rule -> Code -> Test, with test results)
- POC CODE QUALITY REPORT: independent AI code review score and findings
- The notes, the matrix and the code review are the only sources of results.
- From round 2: CURRENT VERSION, GAP REGISTER (from the independent reviewer), OWNER'S NOTES and CROSS-PACK GAPS

## 5. Processing Instructions
1. State the one architecture question tested and why it was the part of the solution that most needed evidence before recommending it.
2. Describe what was built or run, with which tool and model, within the 60-75 minute time-box, and how it was built spec-first: Story -> Spec -> DSL (rules) -> Code -> Test.
3. Describe the method and the synthetic test data.
4. Report results ONLY from the owner's notes. If no results are in the notes yet, write 'Pending: not yet run' and invent nothing.
5. State what was learned, what remains unproven, and whether the D2 decision still holds.
6. From round 2 onwards, remediate instead of rewriting: fix every Open Critical and High gap in the gap register first, then Medium gaps, then the owner's notes and any cross-pack gaps. Change nothing else. Owner notes win when they conflict with anything else.
7. Before answering, check every section below is present, within the length limit, and consistent with the team documents.

## 6. Rules and Constraints
- Length: about 1 page.
- This is not a documentation competition. Concise and coherent beats comprehensive. Stay within the length limit; the reviewer treats padding as a gap.
- Use only facts from the case and the team documents. Never invent numbers, systems, results or policies.
- Anything assumed is labelled ASSUMPTION and listed. State assumptions rather than silently inventing missing facts.
- Keep the exact section names below, in this order. No extra sections. If a section has nothing, write "None identified".
- Plain, professional language a senior stakeholder can read in minutes. No filler, no marketing tone.
- AI-assisted outputs in the design stay reviewable and governed; people take the high-impact decisions.

## 7. Output Format
Return Markdown with these headings, exactly. From round 2, after the document, write a line containing only ===CHANGE LOG=== followed by one line per gap you addressed: `G-01 -> what you changed -> where`. List any gap you could not fix, and why.

### POC Question and Why It Mattered Most
### What We Built or Ran (tool, model, time-box)
### Method and Synthetic Test Data
### Results (from our run only)
### Traceability and Code Quality (requirements fully traced, tests passing, code quality score, open findings)
### What We Learned
### What Remains Unproven
### Effect on the Decision
### Checklist
- [ ] Every required section present, in order, within the length limit
- [ ] Every fact and number traceable to the case or a team document; assumptions labelled
- [ ] Consistent names, numbers and options with the team documents
- [ ] Nothing invented, including results and AI-use claims
### Open Questions

## 8. Quality Criteria
The evidence answers one meaningful architecture question. A full application is not expected. Complete, consistent, traceable, actionable and easy to review.

## 9. Example and Anti-patterns
- Good: "10-12% of work items need manual intervention (case); we target 6% within 12 weeks (ASSUMPTION A2, to validate with ops data)."
- Bad: "The process is inefficient and needs modernisation." (no evidence, no number)
- Bad: three pages where one would do. Length is not quality.
